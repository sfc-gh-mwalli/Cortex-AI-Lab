The Narrative

Healthcare organizations managing value-based care contracts — ACOs, bundled payments, quality bonus programs — must answer two types of questions at scale:

  1. Analytical questions over structured data — "Which patient populations are driving the highest total cost of care? Where are we seeing avoidable ED utilization?" These answers live in claims, encounters, and clinical measures.
  2. Clinical questions over unstructured data — "What does this patient's care history show about gaps in their chronic disease management?" These answers live in clinical notes and care plans.

Today you will build the core components of a VBC care intelligence platform that bridges both.

3. Set Up Your Warehouse, Database & Schema

Next, create a SQL file in your workspace and run the setup script. It converts your trial account's COMPUTE_WH warehouse to an Adaptive warehouse and creates your personal database and schema.

About Snowflake warehouse types

A virtual warehouse is the compute that runs your queries. Snowflake offers several warehouse types — you'll see them in the Type dropdown when you create or edit a warehouse:

  • Adaptive (Recommended) — Snowflake automatically scales compute to the needs of each query. You don't choose a size, configure multi-cluster settings, tune Query Acceleration, or manage suspend/resume — Snowflake handles it. Converting an existing warehouse to Adaptive is an online operation with no downtime.
  • Standard (Gen2) — the next generation of standard warehouses, with new hardware and software optimizations for workloads that need more performance. You pick a fixed size (X-Small, Small, Medium, …) and manage scaling yourself.
  • Standard (Gen1) — Snowflake's original standard virtual warehouses, also sized and scaled by you.
  • Snowpark-optimized — warehouses with a larger memory and cache per node, often used for memory-intensive Snowpark and machine learning operations.

Snowflake also offers Interactive warehouses for very low-latency dashboards and applications, which are created separately and aren't used in this lab.

Adaptive warehouse settings

Instead of a size, an Adaptive warehouse has two optional settings. Our setup script sets both:

  • Max query performance level (MAX_QUERY_PERFORMANCE_LEVEL) — the upper bound of performance for any individual query, expressed in familiar t-shirt sizes (X-Small through 4X-Large). Snowflake only scales a query up to this level when it's confident that will make it faster; simple queries may use less. We'll cap it at LARGE (the default is X-Large).
  • Query throughput multiplier (QUERY_THROUGHPUT_MULTIPLIER) — controls how many queries, and how much total work, the warehouse can run at the same time. Higher values reduce queuing but allow higher spend at any given moment. Valid values are 0 (unlimited) or any whole number of 2 or more. We'll use 2, the default and lowest finite value.

Together, these let you balance speed against spend without picking a warehouse size. You can learn more in the Adaptive Compute documentation.

Module 2 · Step 7

Cortex Search Overview

⏱ ~5 min

What Is Cortex Search?

Cortex Search is Snowflake's fully managed search service for text. You point it at a text column in a table, and it indexes that column and answers search queries against it. You don't manage infrastructure, train a model, or build a pipeline. As part of indexing, it creates a vector embedding for each row: a list of numbers that represents what the text means, so text with similar meaning gets similar numbers.

Every query uses hybrid search, which combines three steps:

  1. Vector search finds notes whose meaning is close to the query, using the embeddings.
  2. Keyword search finds notes that contain the query's exact words and phrases.
  3. Semantic reranking reorders the combined results so the most relevant notes come first.

Together these find more of the right notes than either kind of search alone, which matters for specialized text like clinical documentation.

What semantic search means

Keyword search finds documents that contain the words you typed. Semantic search finds documents that mean what you asked, even when they use different words.

That matters a lot in clinical notes, because clinicians write in their own shorthand. A care manager who searches for "patient who can't breathe and isn't using their inhaler" should find notes that say "increased shortness of breath and wheezing" and "reports non-adherence to prescribed inhalers", even though none of those notes contain the search phrase.

What We're Doing in This Lab

The lab includes 1,510 AI-generated clinical notes for Synthea patients, in a CSV file called Clinical_Notes_RAW.csv. Each note uses the SOAP format: Subjective, Objective, Assessment, Plan. Most notes cover lung cancer, COVID-19, COPD and emphysema, and a small number contain personal data that shouldn't be stored.

In this module you will:

  1. Use AI_COMPLETE to scan every note for personal data and for details that don't match the patient record
  2. Load the notes into a CLINICAL_NOTES table in VBC_LAB.CARE_ANALYTICS, with AI_REDACT removing personal data as the rows are written
  3. Create a Cortex Search service, CLINICAL_NOTES_SEARCH, on that table
  4. Test the service with searches in the Playground
🤖
Why this matters for Module 3: Like Cortex Analyst, Cortex Search does one job: it returns the notes that best match a query. It doesn't write an answer. In Module 3 you'll give a Cortex Agent both tools: Cortex Analyst with the semantic view from Module 1, for metrics, and this search service, for clinical notes. The agent decides which tool each question needs, calls one or both, and writes the answer.

Other Example Uses for Cortex Search

  • Searching provider directory and formulary documentation
  • Surfacing relevant clinical protocols for specific diagnoses
  • Finding prior authorization documentation for specific medications
  • Identifying patients with similar care gaps across a large population
  • Making contracts, policies, or compliance documents queryable by plain language

While You Wait — How Notebook Compute Works

The service you just created is a container that Snowflake manages for you on Snowpark Container Services. A notebook draws on two kinds of compute, billed separately:

  • A compute pool runs the Python kernel. A compute pool is a group of virtual machines (nodes) that runs container workloads, much as a warehouse runs SQL. Your service takes one node on SYSTEM_COMPUTE_POOL_CPU, and the pool bills for as long as the service is running, whether or not a cell is executing.
  • Your warehouse (COMPUTE_WH, which the notebook's first cell selects) runs the SQL cells, including the Cortex AI Function calls. It bills only while those queries run.

Notebooks aren't the only feature that runs on compute pools. Every account comes with two Snowflake-managed pools, SYSTEM_COMPUTE_POOL_CPU and SYSTEM_COMPUTE_POOL_GPU, and Snowflake runs dedicated pools for some features:

  • Notebooks — each notebook service belongs to one user and occupies one node. Every notebook you connect to the same service shares that node.
  • Streamlit apps on the container runtime — each app runs as a long-lived service, and three apps share a node on SYSTEM_COMPUTE_POOL_CPU. An app with no viewers for three days stops on its own. Apps on the warehouse runtime use a warehouse instead of a pool.
  • Next.js apps (Snowflake App Runtime) — a newer way to build full web applications, not just dashboards, that run inside Snowflake next to your data. Each app runs as an Application Service on a Snowflake-managed compute pool. To see one, open a workspace and choose + Add new → Next.js App.
  • Other container workloads — model serving, ML jobs and your own Snowpark Container Services apps also run on compute pools.

Stopping the charges happens in two layers. The notebook service suspends when it reaches its idle timeout, which starts counting once every running cell has finished, or when you suspend it yourself. Once nothing on the pool is running, the pool suspends itself after its own auto-suspend period and stops billing. That's why you set the timeout to 1 hour: it's long enough that the service won't stop while you're still reading results or re-running cells, and short enough that a forgotten service doesn't keep the pool running for a day.

If something goes wrong, click the ▾ chevron next to the Connected button to access kernel controls:

  • Restart kernel — Clears all variables but keeps packages. Use this if a cell gets stuck or produces an unexpected error mid-run.

What the Notebook Does

  1. Setup & Stage — Sets the session context to VBC_LAB.CARE_ANALYTICS, creates an internal stage, and copies the CSV from your workspace onto it. A preview shows raw rows read directly from stage — no table exists yet.
  2. AI_COMPLETE — Data quality scan (~1–5 min) — An LLM (claude-haiku-4-5 by default; the cell comment lists others you can try) reads every note and flags two kinds of issue: personal data in the note text (SSNs, phone numbers, email addresses, physical addresses) and notes whose stated age or gender doesn't match the patient record. Only rows with issues are returned.
  3. Save the flagged rows — A short Python cell saves the flagged note IDs and their quality reports to a temporary table, so the SQL cells that follow can use them.
  4. AI_REDACT — Preview — For the flagged rows, shows what personal data was found and which placeholder will replace it (for example [NATIONAL_ID], [EMAIL], [ADDRESS]) before anything is written.
  5. AI_REDACT + Load (~1–2 min) — Creates the final CLINICAL_NOTES table by reading the stage once. Flagged rows have their personal data replaced as they're written; all other rows pass through unchanged. The raw personal data never reaches a table.
  6. Create Cortex Search Service — Creates CLINICAL_NOTES_SEARCH on the clean table, then runs a test search to confirm it works.
✅
Checkpoint: The final cell searches for "mucoviscidosis with pulmonary exacerbation". Mucoviscidosis is an older name for cystic fibrosis, and the word doesn't appear in any note. If the results are about cystic fibrosis (CF) patients, semantic search is working.

Part 4 — When the Notebook Service Stops

Your notebook service, and the compute pool node it occupies, keep running and billing until the service is suspended. Shutting down the kernel, closing the notebook tab or closing your browser doesn't stop it.

For this lab, leave the service running. You may want to come back to the notebook later, and a suspended service takes another 3–5 minutes to start again. You don't need to do anything to stop the charges: because you set the idle timeout to 1 hour in Part 2, the service suspends itself one hour after your last cell finishes. With the 24-hour default, it would have kept running for a day.

Outside the lab, when you know you're done with a notebook, you can suspend its service yourself instead of waiting for the timeout. Click the ▾ chevron next to Connected and select Manage service, which opens Monitoring » Services & jobs. Then click the ⋮ menu at the end of the service's row and select Suspend. (Drop deletes the service entirely.)

Whichever way the service suspends, it disconnects the notebook and clears the kernel's memory: variables, cell results and any packages you installed. It doesn't touch the objects the notebook created in Snowflake. CLINICAL_NOTES, CLINICAL_NOTES_SEARCH, NOTES_STAGE and NOTES_CSV all stay in place, and the search service keeps answering queries for the rest of the lab. To use the notebook again after it has suspended, open it and click Connect or run a cell; the service resumes in a few minutes, and you'll need to run the cells again from the top.

What is a Semantic View?

A semantic view is a native Snowflake object — defined using SQL DDL and stored at the schema level — that organizes business metrics, dimension relationships, and domain logic directly in your database. Rather than embedding business logic in every query or BI tool, you define it once in the semantic view and it becomes the authoritative source for how your data should be interpreted.

Semantic views power Cortex Analyst, Snowflake's natural language query engine. Once a semantic view is in place, users can ask plain-language questions and get accurate SQL-backed answers — because the semantic layer already knows what the data means.

2. Add Metrics and Dimensions

Beyond what Autopilot generates, we need two types of additions for this lab:

  • Metrics are named calculations — business measures defined once in the semantic view so every query uses the same logic. For example, Average Cost per Encounter is AVG(total_claim_cost). Without a metric, Cortex Analyst has to guess the formula each time. Autopilot suggested a few metrics in the Suggestions panel, but for this lab we'll add a specific set of VBC metrics instead.
  • Dimensions are attributes used to slice and filter data. Most dimensions come directly from a column, but expression-based dimensions are derived from logic. For example, Patient Income Band isn't a column in the data — it's a CASE expression that buckets the INCOME value into ranges like <30k, 30-60k, etc. These let Cortex Analyst answer questions like "show cost by income band" without any transformation in the query.

Module 1 · Step 6

Ask Value-Based Care Questions

⏱ ~5 min hands-on

The Playground is where you test the semantic view before anyone else relies on it. When you ask a question in plain English, Cortex Analyst uses VBC_ANALYTICS_SV to turn it into SQL and runs that SQL. Your job here is to check that the conversion is right: that the question maps to the correct metrics, dimensions and joins, and that the answer makes sense.

Cortex Analyst is not an agent

It's easy to blur these two together, so be clear on what you're testing here. Cortex Analyst with a semantic view does one job: it turns a plain-language question into SQL and returns the results. It doesn't plan, pick between tools, look at documents, or reason about what the numbers mean. A Cortex Agent is the layer that does that work, and it uses Cortex Analyst as one of its tools.

Question 2 below shows the difference. Cortex Analyst will tell you the avoidable ED rate for the lowest income band is roughly five times the rate for the highest. That's the whole answer. It won't tell you why, or what to do about it. An agent can take that result, search the care notes for those patients, and explain what's driving the gap.

🎯
Why test here first: when an agent needs numbers, it hands the question to Cortex Analyst and this semantic view. If the SQL is wrong here, the agent's answer is wrong too, no matter how well it reasons. Get the semantic view right in the Playground, and every agent that uses it inherits that accuracy.

With VBC_ANALYTICS_SV open in Semantic Studio, open the Playground tab in the right panel and submit one of the questions below (or one of your own). For each answer, check:

  • The interpretation matches what you meant. Cortex Analyst restates the question under "This is our interpretation of your question". If that restatement is off, the SQL will be too.
  • The semantic query uses what you just added. Expand Semantic query under the results. For Question 1 you should see METRICS avg_cost_per_encounter DIMENSIONS patients.patient_income_band, which means Cortex Analyst used your new metric and dimension instead of improvising a calculation.
  • The results are plausible. Rates should fall between 0 and 1 (or 0 and 100%), costs should be positive, and every income band should appear.

If an answer is wrong, the fix usually belongs in the semantic view (a clearer description, a synonym, or a missing metric), not in the question. That edit, test, and fix loop is how a semantic view gets reliable enough to put in front of business users.

Save good answers as verified queries

When an answer is correct, click + Add to verified query below the semantic query. This saves the question and its SQL into the semantic view's Verified Query Repository: a set of known-good question and SQL pairs that you, the semantic view owner, have signed off on.

  • Better accuracy. When a user asks the same or a similar question, Cortex Analyst uses the verified SQL instead of generating a new query from scratch.
  • Consistent answers. Everyone who asks "average cost per encounter by income band" gets the same, approved logic, whether they ask here or through an agent.
  • Smarter suggestions. Snowflake can analyze your verified queries to suggest new filters, metrics and descriptions for the rest of the semantic view, so it gets better at questions you haven't verified yet.

Verified queries are stored in the semantic view itself, so adding one is an edit like any other: it isn't live until you publish.

  1. Run Question 1 and confirm the results look right.
  2. Click + Add to verified query. The editor scrolls to the Verified queries section and shows the new entry, highlighted, with the question and its SQL.
  3. Review the entry, then click Keep at the top right of it. (Undo discards it.) Until you click Keep, the change is only proposed.
  4. Click Publish changes, make sure the default target is checked (it shows Out of sync), and click Publish. If the dot doesn't appear on Publish changes, refresh the page as you did earlier.
  5. The Review publish changes dialog opens with an Overwrite warning and a diff of your file against the published semantic view. The warning is expected: publishing always replaces the semantic view object with your workspace file. The only change should be a new verified_queries: block at the end, containing:
    • name and question: the question you asked
    • sql: the semantic query Cortex Analyst generated
    • verified_at and verified_by: when you verified it, and your username
    • use_as_onboarding_question: false: set this to true if you want the question offered to users as a suggested starting question
    If that's all you see, click Publish.
⚠️
Only verify answers you've checked. Cortex Analyst trusts verified queries, so a wrong one teaches it the wrong logic and makes similar answers worse. If the SQL is close but not right, fix it before you save it.
Module 3 · Step 10

Why Agents?

⏱ ~30 minutes total
⏱ 3 min — Business Context

You now have two tools, and each does one job. Cortex Analyst turns a question into SQL over VBC_ANALYTICS_SV and returns the results. Cortex Search returns the clinical notes that best match a query. Neither one can answer a question that needs both kinds of data, and real care management questions often do:

💬
"This patient was admitted three times this year. What's driving it, and does their care plan address it?"

Answering that takes both their utilization data and their clinical notes. A Cortex Agent can do it: it works out which tools the question needs, calls each one, and combines the results into one answer.

Key Concepts

  • Tool orchestration — You give the agent a set of tools (here, Cortex Analyst and Cortex Search) and instructions for when to use each. It picks the tools for every question, so you don't write routing logic.
  • Multi-tool answers — For questions that span both kinds of data, the agent calls several tools and combines their results into one answer.
  • Scope — An agent can only reach data through its tools, and its instructions set what it should answer. This agent's instructions tell it to decline questions outside its two data sources.
  • Auditability — Agent requests, including which tools were called, are logged and can be reviewed later. That matters in a regulated field like healthcare.

VBC Use Cases

  • Care manager co-pilot — surface patient risk from notes + utilization trends in one answer
  • Quality analyst assistant — combine protocol documentation with HEDIS measure data
  • Population health dashboard back-end — answer complex cohort questions automatically
  • Prior auth triage — match policy documentation with patient claims history

Part 2 — Review the Agent in Snowsight

After CoCo confirms the agent was created, open it in Agent Studio. There's no separate Edit mode: the agent page opens with all its settings on tabs (Overview, Configuration, Access, Evaluations, Observability, Preview).

  1. In the Snowsight left nav, go to AI & ML → Agent Studio
  2. Click on VBCCAREAGENT. The page opens on the Overview tab, which shows an agent readiness checklist and usage for the last 7 days (all zeros for now). Under the agent name you'll see VBC_LAB · CARE_ANALYTICS and an Added to Snowflake CoWork label, which confirms the CoWork setup step in the prompt worked.
  3. Click the Configuration tab. It has five sub-tabs: General, Instructions, Tools, Skills, and MCP. Click through the first three:
    • General — confirm Display name is VBC_CARE_AGENT. Description holds a one-line summary CoCo wrote. These are what users see; they don't change how the agent behaves. Example questions is empty, and you can leave it that way.
    • Instructions — Model is set to auto, so Snowflake picks the model that plans each answer. Below it are the two instructions from your prompt. Orchestration instructions tell the agent which tool to use for which kind of question: VBCAnalytics for costs, utilization, and quality measures; ClinicalNotes for notes and care gaps; both when a question needs numbers and clinical context. Response instructions set how it answers: cite the source, lead with the direct answer, and make no clinical recommendations.
    • Tools — confirm both tools are listed. Under Query structured data, VBCANALYTICS uses semantic view VBC_LAB.CARE_ANALYTICS.VBC_ANALYTICS_SV and a warehouse (usually COMPUTE_WH). Under Search documents and unstructured data, CLINICALNOTES uses service VBC_LAB.CARE_ANALYTICS.CLINICAL_NOTES_SEARCH. The Code Execution tool toggle at the top stays off.
  4. The last two sub-tabs hold capabilities this agent doesn't use, so leave them empty:
    • Skills — agent skills are reusable workflows. Each one is a folder with a SKILL.md file of instructions (and optional scripts) stored in a stage or Git repository. The agent reads each skill's name and description to decide when to use it. You'll see No skills added, with Add skill and Add skill with Cortex buttons at the top right.
    • MCP — connects the agent to a remote MCP server, such as Atlassian Jira or Salesforce, so it can call the tools that server provides.

Finding your way around: CoWork has no panel on the right; the conversation takes up the middle of the page. The left navigation has New chat, Artifacts, Automations, Capabilities, and Search. Two of these are worth knowing about for later:

Wrap-Up

Key Takeaways & Next Steps

⏱ ~5 min

What You Built Today

  • 📊Cortex Analyst + Semantic View — turns plain-English questions into SQL over shared VBC definitions. You tested the conversion in the Playground and saved a checked answer as a verified query, so similar questions get consistent results.
  • 🛡️Cortex AI Functions — in the loading notebook, AI_COMPLETE scanned 1,510 clinical notes for personal data and quality issues, and AI_REDACT removed that personal data as the rows were written, so it never landed in a table. The AI ran in SQL, inside the load.
  • 🔍Cortex Search — makes clinical notes searchable by meaning. Care managers can find relevant patient history in plain language, even when the notes use different words.
  • 🤖Cortex Agent — connects clinical notes and structured data. It plans which tools a question needs, calls them, and combines the results into one answer.
  • 🧠Snowflake CoWork (formerly Snowflake Intelligence) — surfaces the agent as a polished conversational UI for business users, no SQL required.
  • ❄️Everything runs inside Snowflake — the data, models and agent stay within Snowflake's security and governance boundary, with no separate AI infrastructure to stand up. That simplifies security and compliance reviews in regulated settings such as HIPAA.
